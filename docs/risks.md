# Risk Register

Risks identified across product, UX, technical, and operational dimensions. A risk earns a row here when it could plausibly derail the Vision, MVP, or a specific feature/ADR — not every hypothetical worry.

| ID | Risk | Likelihood | Impact | Mitigation / Owner | Status |
|---|---|---|---|---|---|
| R1 | Auto-completing skipped interruptions (Return to Original Task) could mask genuinely unfinished work if indistinguishable from an explicit completion. | med | med | **Mitigation restated 2026-07-28** — the field it named was retired. Was: "Time Blocks record a `completion_reason` (`explicit` vs `auto-completed-on-skip`)." Now: skipped work carries `InterruptionOutcome::Skipped`, surfaced through the mandatory `DerivedInterruptionStatus` projection so no view can silently equate it with completed work. Two caveats the second-pass review surfaced: (a) the guarantee now depends on every consumer using that projection rather than reading the persisted field, since an absent value is ambiguous; (b) `Skipped` is a *narrower* claim than the old pairing — it says the work was never resumed, not that it was auto-completed. See the Event Model ADR and `docs/glossary.md`. | mitigated (by design; not yet implemented; depends on the projection rule holding) |
| R2 | Export-time aggregation by exact match on name/project/client can silently fragment historical billing totals if a task's name, project, or client is renamed or entered inconsistently over time — no persisted Task identity exists to catch this. | med | med | Partially mitigated going forward by Task Templates (`docs/product/features/task-templates.md`): consistent selection from a template reduces *entry-time* typos/drift for new Time Blocks. Does **not** close the underlying gap — editing an existing template's name/project/client explicitly does not retroactively update Time Blocks already recorded under the old values (by design, per the flat-timeline model), so a template rename mid-life reproduces the same fragmentation this risk describes, just less often. No reconciliation/rename tool exists yet. This exact-match grouping is now concretely implemented (not just described) in `docs/product/features/export.md`'s XLSX row structure — the risk becomes visible directly as under/over-reported task rows in the exported sheet. Revisit if real usage shows fragmentation. | open |
| R3 | Fully manual tracking (no idle/gap detection in MVP) depends entirely on user discipline; nothing prevents forgetting to log a Switch/Interrupt, which directly undermines the Vision's accurate-record promise. | med-high | high | Was "None in MVP — consciously deferred." **Amended 2026-07-28:** the Concept revision brings timeline reconstruction into MVP scope (`docs/product/mvp.md`), which gives this risk its first actual mitigation — work that went untracked can be drawn in afterwards rather than lost. This mitigates *consequence*, not *cause*: nothing still prevents forgetting, and the user must notice the omission themselves. Detection remains deferred (`docs/vision/vision.md` Non-goals). Note the mitigation introduces R10, which partly works against it. **The mitigation is scheduled, not in place** — it depends on the Event Model ADR and a feature doc that do not exist yet. Pointer corrected the same day: this previously cited `ideas/manual-time-block-entry.md`, which `CLAUDE.md` explicitly excludes from the project's rigour guarantees, so it was never a legitimate mitigation reference. See `docs/assumptions.md` **A1** (and **A11**, which partly works against it). | open (mitigated in consequence only, and only once built; cause unaddressed by design) |
| R4 | A `recovered-gap` entry's inferred end time can be wrong if the user never notices/corrects it in the dashboard before exporting, undermining "data the author would actually trust and use for billing" (`docs/vision/vision.md`; citation updated 2026-07-28 — the criterion no longer says "without hand-editing"). Depends on the same user-discipline gap as R3. | med | high | A fixed 60-second heartbeat write while an entry is active bounds the inference error to roughly a minute (not hours), and the dashboard surfaces `recovered-gap` entries distinctly (not folded into `explicit`), inviting correction — but nothing enforces that the user actually reviews/corrects them before exporting. `docs/product/features/export.md` explicitly considered and rejected enforcing review at export time (author's own workflow discipline instead) — this is now a confirmed design choice, not an oversight. **Amended 2026-07-28:** this mitigation was overstated. It assumed correction was merely *unenforced*; in fact no correction mechanism exists at all (see **R9**), so a user who does notice a wrong inferred end time still cannot fix it. The heartbeat bound (~60s) and the distinct surfacing of `recovered-gap` entries both hold; the "inviting correction" half does not, because the invitation leads nowhere. R4 cannot be closed before R9 is. | open (staleness bounded by design; correction is unavailable, not merely unenforced — see R9) |
| R5 | A torn write (process killed mid-write to the persisted transition log) could corrupt more than just the latest transition if the storage format isn't append-only/atomic at the record level. | low | high | **This risk was realised, and this row previously described a mitigation that did not hold.** It read: "a torn write can only affect the last, unreplayed record… every prior record is untouched." Prior records were indeed untouched — but **everything written *after* a torn write was permanently destroyed**, which the wording implied was impossible. Root cause: the torn fragment had no trailing newline and was never removed, so the next record was appended onto the same physical line; `decode_line` splits on the last tab, so the checksum was verified over fragment+json, mismatched, and replay broke there on every subsequent run. Across three sessions after a tear, none survived, `next_seq` stalled so every session reissued the same `seq`, and the bytes remained on disk — unreachable, not absent. **Now genuinely mitigated and implemented** ([`78096a8`](https://github.com/DeLicious777/Anchor/commit/78096a8), issue #18): on every `LogWriter::open`, bytes after the final record boundary are truncated, so the log always begins an append at a record boundary. Committed history is never touched — the truncation cannot cross a newline — and only unfinished writes, which `append` never acknowledged to their caller, are discarded. Replay then resumes normally. Detection remains as [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md) specifies. Two limits, both stated: it prevents future damage but does not recover an already-damaged log, and it repairs the tail only at `LogWriter::open`, so a fragment left mid-session by a failed or partial `write_all` is not repaired before the next append — the same concatenation damage, within one session, and the reason **R14** covers `write_all` and not only `sync_all`. | mitigated (implemented and regression-tested, 2026-07-29) |
| R14 | **A `seq` can be consumed by an append that did not fully and durably complete.** `LogWriter::append` does `write_all` → `sync_all` → `next_seq += 1`, so `next_seq` advances only if *both* succeed — while bytes may already have reached disk either way. Two variants, and the second is the more damaging: **(a) failed `sync_all`** — a complete, checksum-valid line for that `seq` may be on disk, so the next append reuses the number and produces two readable lines with the same `seq`. **(b) failed or partial `write_all`** — an unterminated fragment is left mid-session, and `truncate_incomplete_tail` only runs at `LogWriter::open`, so the next append is concatenated onto it, reproducing R5's permanent-loss damage *within the same session* rather than across a restart. In both, the error surfaces as a string (`commands.rs`) and the app continues with the same writer. | low | high | None yet. Two consequences: it makes [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md)'s watermark filter undefined for the affected lines, and it is a **stated prerequisite of [ADR 0006](decisions/0006-stable-persistent-time-block-identity.md)** — under a `seq`-derived identity scheme, duplicate `seq` means two Time Blocks share an id, and `stack.rs`'s `resolve_paused` and `derived_status` both use `id` as a lookup key, so the wrong block is resolved silently rather than loudly. Distinct from R5, which covered the torn-tail path and is now fixed; this path is unaddressed. Fix belongs in the writer: `seq` must not be consumed by a write that did not durably complete. | open |
| R6 | Tauri's ecosystem is younger/less battle-tested than Electron's, and this is a solo project with a real (not "narrow") Rust surface area — hotkeys, tray, window management, log I/O/compaction, heartbeat timer, and OS-level sleep/hibernate detection (which requires raw Windows API calls, not a Tauri-provided feature). For a single maintainer, ecosystem gaps or unexpected platform-API complexity could stall MVP progress more than a more mature/higher-level stack would. | med | med | None specific yet — accepted as the cost of satisfying the memory/startup priorities and frontend-stack constraint together (see ADR 0002). Revisit ADR 0002 if `tauri-plugin-global-shortcut` lacks conflict detection or sleep/hibernate detection proves substantially harder than expected. | accepted |
| R7 | Compaction (snapshot + log truncation, [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md)) introduces a second on-disk artifact whose own write can be interrupted — a crash mid-snapshot-write, or between a successful snapshot write and log truncation, could otherwise cause double-replay or data loss if handled naively. | low | high | Mitigated by design: a watermark (sequence number) recorded in each snapshot makes replay correct regardless of when a crash occurs relative to truncation — log truncation becomes a disk-space optimization, not a correctness dependency. Snapshot writes use write-temp-then-atomic-rename. See ADR 0004 Consequences. | mitigated (by design; not yet implemented) |
| R8 | Naming is now optional at start time (Switch/Interrupt hotkeys auto-assign `Anchor N` if left blank, `docs/product/features/interruption-stack.md`) — a task left un-renamed reproduces R2's export-time aggregation fragmentation, but under a meaningless generic name instead of a typo'd real one, making the fragmentation harder to spot in an exported sheet (an `Anchor 3` row reads as intentional, not as a forgotten rename). | med | med | Rename is available at any point while a task is active, with autocomplete over both Task Templates and past task history to make correcting it fast. Nothing enforces that the user actually renames before exporting — same accepted user-discipline basis as R3/R4. | open |
| R9 | An accepted feature doc describes a capability that does not exist. `docs/product/features/interruption-stack.md` states `recovered-gap` entries are "user-correctable" and that "correction happens whenever the user next opens the dashboard" — and R4's mitigation depends on it — but nothing implements it: `TransitionPayload` (`app/src-tauri/src/model.rs`) has no variant that edits a completed Time Block's times (`RecoverGap` carries an `inferred_end` but only *closes* an entry), and `app/src-tauri/src/commands.rs` exposes no edit or delete command for a Time Block, only template CRUD. Beyond leaving R4 unmitigated, this is a second-order risk to the whole register: an accepted doc was trusted as describing built behavior during review, so other accepted-doc claims may warrant the same check. | certain (already true, not probabilistic) | high | None yet. Captured in `ideas/manual-time-block-entry.md`. Correcting a `recovered-gap` end time and adding a forgotten Time Block by dragging a span are the same underlying capability — mutating the historical timeline after the fact — and should be designed together under one ADR rather than solved twice. That ADR is non-trivial: it needs a transition type carrying **both** an explicit start and end (none exists today), and it breaks [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md)'s implicit assumption that `seq` order implies chronological order, since a block entered at 16:00 for a 09:00 span is logged after blocks that happened later than it. Overlap rules are also undefined and matter for billing, since `docs/product/features/export.md` sums durations per task. Upside: the same capability is the obvious mitigation for **R3**, which currently has none. **Amended 2026-07-28:** the Concept revision moved timeline reconstruction into MVP scope, so this is no longer an unmitigated documentation/implementation gap — it is now premise-critical scope with a planned resolution. The ADR is still unwritten and the capability still does not exist, so the risk stays open; what changed is that it is now scheduled rather than deferred. The edit surface was then **narrowed** by the `grill-with-docs` session to five operations — add, move, resize, edit identity, delete — with split and merge removed for lacking problem statements. Owned by `docs/product/mvp.md` and the pending Event Model ADR, not by `ideas/`. R4 still cannot close before this does, and closing this row must **not** close R11. **Amended 2026-08-01:** the design now exists and is accepted — [`timeline-reconstruction.md`](product/features/timeline-reconstruction.md), with [ADR 0005](decisions/0005-event-model-time-block-metadata-and-reconstruction-transitions.md) supplying the event model and [ADR 0006](decisions/0006-stable-persistent-time-block-identity.md) the persistent identity that lets a reconstruction transition name a block from an earlier session. Its acceptance criteria include the R9 path end to end: correcting a `SystemInferred` end leaves the block `UserDetermined` and it stops rendering as inferred. **The risk stays `open`, and the distinction matters** — what closes it is a *shipped correction mechanism*, not an accepted document. This row exists precisely because an accepted doc was once trusted as describing built behaviour ([`principles.md`](principles.md) #8); closing it on a design would repeat that error in the register that was created to catch it. Implementation is additionally gated on **R14**. | open (designed and accepted 2026-08-01; unimplemented) |
| R10 | An always-available reconstruction workspace may erode the in-the-moment capture discipline the product depends on. If the timeline can always be fixed later, the exception path (manual entry) quietly becomes the default, and Anchor re-creates the after-the-fact guesswork it exists to eliminate — while `docs/concept/concept.md` still claims to be "capture-first, timeline-assisted." | med | high | None. Inherent tension in the 2026-07-28 Concept revision, accepted knowingly: reconstruction is what makes R3 survivable, and the same capability is what could undermine capture. Notably this risk *increases* as reconstruction gets better. No metric currently distinguishes a day that was captured from a day that was reconstructed — adding one would make this observable rather than a matter of self-report. Only real usage answers it; see `docs/assumptions.md` **A11**. Capture Rate (`docs/vision/vision.md`) now makes this falsifiable rather than a matter of self-report. | open |
| R11 | **Architectural decisions made on assumptions never verified against either the documentation or the implementation.** The failure mode is broader than drift: sometimes the docs were wrong, sometimes the implementation was ahead of the docs, sometimes both were incomplete while decisions were being made on top of them. The common cause is that no step establishes which source is authoritative before a decision depends on it. | high | high | None yet. **Evidence — six instances found in the 2026-07-28 session alone, only because someone went looking:** (1) R9, an `accepted` doc promising `recovered-gap` correction with no mechanism; (2) pause decided as "Complete + Start," impossible because `Complete` is rejected while the stack is non-empty (`app/src-tauri/src/stack.rs`); (3) `explicit` documented as "user-finished" while the code writes it at six sites for four different meanings; (4) Switch's stack behaviour undocumented while a Vision promise depended on it; (5) [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md) specifying compaction's mechanism but never its snapshot payload, which was load-bearing for a decision this session; (6) compaction unimplemented while several docs reasoned about what survives it. Case (2) is the clearest cost: a decision was made *wrongly* because nobody checked. **Candidate mitigation:** before any design document reaches `accepted`, every implementation-dependent claim in it must be explicitly verified against either the implementation or a documented architectural decision. That scales to claims about code that does not exist yet. **Note: R9 closing must not close this row** — nothing systemic changes when one instance is fixed. | open |
| R12 | Anchor's flat model (name + optional project/client) may not map onto Produra's project → sub-project → activity hierarchy without loss, despite `docs/vision/vision.md` now making clean transfer a **success criterion** ("a copy, not a reconciliation"). Concretely: `docs/product/features/export.md` fixes the XLSX columns at name/project/client/duration — four columns against a three-level hierarchy *plus* a client. | med | med-high | None. The mapping has never been checked against a real Produra instance or a real booking session; logged as an assumption (`docs/assumptions.md`, 2026-07-28) but previously with no risk row despite being Vision-level. Validation should cover the mapping itself, any information loss, and whether the current export model stays sufficient — and it belongs in Design, not after implementation. If the mapping proves impossible without distorting one model or the other, either the export column structure or the flat model has to give. | open |
| R13 | The visual redesign adopts an external design system built against different assumptions, carrying three unpriced costs: (a) every component is **React JSX** while Anchor is Svelte ([ADR 0002](decisions/0002-desktop-app-framework-and-platform.md), `docs/architecture/constraints.md`), so the component layer is a hand-rebuild with the JSX as reference spec — an estimate nobody has made; (b) it specifies **three font families** (Familjen Grotesk, Hanken Grotesk, JetBrains Mono), which must be bundled since a desktop app has no guaranteed network, against an ADR 0002 that chose Tauri partly for memory and binary size; (c) `app/src-tauri/tauri.conf.json` ships **`"csp": null`**, disabling content-security policy — a live security posture, flagged in `docs/product/features/visual-redesign.md` as "worth revisiting" and nowhere else. | med | med | None. (a) and (b) are cost/scope risks to be sized during the redesign's Design pass. (c) is independent of the redesign and should not wait for it — `csp: null` was scaffold default, not a decision, and warrants its own ADR or a straight fix. Added 2026-07-28 after the second-pass review found the register had grown by two rows without covering any of this. | open |

- **mitigated** — a concrete mitigation is in place
- **accepted** — consciously not mitigating; the cost of mitigation exceeds the risk
- **realized** — it happened; document what actually occurred and link any resulting ADR or assumption update
