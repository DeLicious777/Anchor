# Glossary

Shared vocabulary for this project. A term earns an entry here once it's used more than once, is disputed, or gets redefined mid-conversation — typically surfaced during a `grill-with-docs` session via `/domain-modeling`. Feeds Graphify's knowledge graph directly, so keep entries atomic (one term, one definition) rather than prose paragraphs.

| Term | Definition | First defined in |
|---|---|---|
| Time Block | The atomic unit of tracked work: a name, start time, end time, duration, optional project/client, and three independent metadata fields — End Determination, Capture Origin, and Interruption Outcome (revised 2026-07-28; previously a single conflated Completion Reason). Independent entry in the Timeline — not tied to a persistent Task entity. | `docs/concept/concept.md` |
| Timeline | The ordered sequence of all Time Blocks for a user — a **projection of the transition log**, not itself the source of truth (corrected 2026-07-28; previously defined here as "the single source of truth"). All reports and exports derive from this reconstructed state. Purely the **data** — the surfaces that display and edit it are the Timeline Editor and the History View, defined separately below. | `docs/concept/concept.md` |
| Time Block Identity | A Time Block's durable identifier, derived deterministically from the `seq` of the transition that created it: `UUIDv5(ANCHOR_NAMESPACE, seq)` ([ADR 0006](decisions/0006-stable-persistent-time-block-identity.md)). Replaces per-construction random UUIDs, which were regenerated on every replay and therefore could not be referenced across restarts. Exists because timeline reconstruction needs to name an existing block — the first *inter-replay* reference in the product. | [ADR 0006](decisions/0006-stable-persistent-time-block-identity.md) |
| Log Lineage | One continuous history of a single transition log — everything descended from the same log file without it being deleted, recreated, or replaced by a restored copy. **The scope within which Time Block Identity is stable.** Two lineages (a fresh install, a rebuilt log, a second profile) will reuse the same ids for unrelated work; the first block of every lineage has the same id. Global uniqueness across lineages is an explicit non-goal — no accepted requirement asks for it, `export.md` does not specify an `id` field, and the billing path never carries one. | [ADR 0006](decisions/0006-stable-persistent-time-block-identity.md) |
| `ANCHOR_NAMESPACE` | The fixed UUIDv5 namespace constant that Time Block Identity is derived under: `becbca30-958b-4568-a9ec-dd5ed1dbf612`. Chosen once and **never changed** — it is part of the durable contract from the moment any transition references a derived id, since altering it would silently re-identify every block in every log. | [ADR 0006](decisions/0006-stable-persistent-time-block-identity.md) |
| Sequence Number (`seq`) | The monotonically increasing per-line number carried by every transition log record, heartbeats included. Originally introduced for watermark-based replay filtering ([ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md)); since [ADR 0006](decisions/0006-stable-persistent-time-block-identity.md) it is **also** the input to Time Block Identity, which makes its uniqueness load-bearing in a second way. Distinct from the compaction-trigger count, which only increments on lifecycle transitions. | [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md) |
| Transition Log | The append-only event log of every transition and heartbeat — **Anchor's single source of truth**. All state, including the timeline and the interruption stack, is replayed from it. Every input path produces transitions and nothing else: hotkeys, mini widget, timeline edits, and any future import. Format, checksum framing, and compaction are decided in [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md). | [ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md); named as source of truth in `docs/concept/concept.md` (2026-07-28) |
| Timeline Editor | The graphical, direct-manipulation surface where the Timeline is reconstructed. Named for what it *does*, not what period it shows — "day" is inherited from Timeline and would be wrong if other ranges are added later. This is where move and resize exist; they are meaningless against a tabular view, which is why naming it separately was necessary before its scope could be counted honestly. | `grill-with-docs` session, 2026-07-28 |
| History View | The tabular representation of the same Timeline data, for reading and editing work as a structured list. Deliberately not "History Table" — the name describes its purpose, not its widget, so it survives becoming a grouped list or another form. Previously called "the timeline view" in `docs/product/features/interruption-stack.md`, which is what made "Timeline" ambiguous. | `grill-with-docs` session, 2026-07-28 |
| Reconstruction Workspace | The Timeline understood as an editing surface rather than a passive log. The MVP edit surface is exactly five operations: **add, move, resize, edit identity, delete**. Constrained by one rule — every block always represents work that actually happened. The Timeline answers "what happened today?", never "what should happen next?"; Anchor has no future-dated or intended blocks. Split and merge were considered and **removed** (2026-07-28) for lacking problem statements — see [`principles.md`](principles.md) #1. | `docs/concept/concept.md` (2026-07-28 Concept revision) |
| Capture-First, Timeline-Assisted | Anchor's interaction premise: primary capture is instant (sub-second, hotkey or mini widget, without opening the app), because interruptions arrive while the user is looking at something else. The timeline is where work is understood and refined afterwards, not where it is normally entered. Manual timeline entry is the exception path, for work that went untracked or needs reconstructing. | `docs/concept/concept.md` (2026-07-28 Concept revision) |
| Progressive Disclosure (of the stack) | The interruption stack's default invisibility, with an opt-in path to the full picture: the UI shows only the current task and the two return options unless the user opens an interruption-history panel. Inspecting the stack grants no additional return paths — Return to Previous and Return to Original remain the only actions. | `docs/concept/concept.md` (2026-07-28 Concept revision) |
| Switch | A deliberate move from one task to another with no expectation of returning to the one just left. Distinct from Interrupt. **Contract (specified 2026-07-28):** a Switch never modifies the interruption stack — it ends the current block and starts another, and any existing interrupted work stays pending until explicitly resolved. Previously this was the implementation's behaviour but no document guaranteed it, leaving a Vision promise resting on an unspecified detail. | `docs/concept/concept.md`; stack contract specified in the `grill-with-docs` session, 2026-07-28 |
| Interrupt | Pausing the current task because something requires immediate attention, with intent to return; pushes the current task onto the interruption stack. | `docs/concept/concept.md` |
| Interruption Stack | The internal, arbitrarily deep, true stack structure holding nested interrupted tasks in order. Not surfaced in the default UI, but inspectable on demand — see Progressive Disclosure (revised 2026-07-28; previously "Not directly exposed in the UI"). | `docs/concept/concept.md` |
| Return to Previous Task | Resume the most recently interrupted task by stepping back exactly one level in the interruption stack. | `docs/concept/concept.md` |
| Return to Original Task | Jump directly to the root task of the current interruption chain. Every intermediate frame skipped this way has its Time Block marked `InterruptionOutcome::Skipped` (previously `auto-completed-on-skip`, revised 2026-07-28), so skipped work is never silently indistinguishable from work the user actually resumed or finished. Explicitly dismissing a frame reaches the same outcome by a different route — see [`principles.md`](principles.md) #6. | `docs/concept/concept.md` |
| Completion Reason | **Retired 2026-07-28** — superseded by End Determination, Capture Origin, and Interruption Outcome. It conflated three independent questions: how the end time was established, how the block entered the system, and what happened to interrupted work. `auto-completed-on-skip` was the clearest symptom — it described the fate of a stack frame, not a reason a block ended. **No longer present in the code** as of the 2026-07-29 migration; kept here because the term still appears in ADRs and in the git history, and because a reader meeting it there needs the mapping. Use the three fields below in all new work. | `docs/concept/concept.md`; retired by the Concept revision, see the Event Model ADR |
| End Determination | A field on every closed Time Block answering exactly one question: **how was this block's end time established?** `UserDetermined` (the user's own action fixed the moment — Complete, Switch, Interrupt, or Return) or `SystemInferred` (Anchor inferred it after a detected gap, accurate to roughly the heartbeat interval). Nothing about workflow, completion, or resumability lives here. Renamed from Completion Reason because the field never described *completion* — a Switch-ended block's end time is exactly as user-determined as a completed one's. | Concept revision, 2026-07-28; see the Event Model ADR |
| Capture Origin | A field on every Time Block answering: **how did this block enter the system, and how much do we trust it?** Distinguishes work captured live as it happened from work reconstructed afterwards from memory, and records whether a block has since been manually adjusted. Exists because a reconstruction workspace makes reconstructed and live-captured blocks otherwise indistinguishable — the same reasoning that produced Completion Reason originally. Makes the Capture Rate metric answerable and risk R10 falsifiable. | Concept revision, 2026-07-28; see the Event Model ADR |
| Interruption Outcome | An optional **persisted** field answering: **what ultimately happened to this interrupted work?** Absent is genuinely ambiguous on its own — it means either *never interrupted* (the common case) *or* *interrupted and not yet resolved* — so no view may read this field directly; use Derived Interruption Status below. `Resumed` means the user returned to it; `Skipped` means it was interrupted and never resumed — whether by jumping past it via Return to Original Task, or by explicitly dismissing its stack frame. Absorbs the old `auto-completed-on-skip`. There is deliberately no `Pending` value: an unresolved obligation is represented by the stack frame itself, which the snapshot persists. | Concept revision, 2026-07-28; see the Event Model ADR |
| Interruption Stack Frame | An **unresolved obligation to record the outcome of interrupted work**. It carries both the return path (name/project/client) and the only link back to the interrupted Time Block whose outcome is still undetermined. Not merely a navigation aid — this definition is what makes dismissing a frame a historical statement rather than the deletion of a reminder, and it is why Return to Original Task stamps every frame it pops instead of discarding them. | `grill-with-docs` session, 2026-07-28 |
| Pause | **A specialised Interrupt that creates an interruption frame without creating a successor task.** Closes the active Time Block, pushes its frame onto the interruption stack, leaves nothing active. Paused work and interrupted work are the same state by design — *stopped, intending to return* — so the paused task keeps its return path as the top frame, and Pause needs no persisted concept of its own. A paused span produces no Time Block and is never exported. Closes a hole in the accepted design: `Complete` is rejected while the stack is non-empty. | `grill-with-docs` session, 2026-07-28; see the Event Model ADR |
| Continue Session | **A UI action, not a transition.** Indicates tracking may continue after an intentional pause. It changes no state: after Pause the state is already correct, and after a restart replay rebuilds it from the persisted stack. Named for the *tracking session*, never a task — "Resume" would imply Anchor knows when work restarted, which it cannot. **Note:** `app/src-tauri/src/power.rs` currently auto-starts a block after gap recovery on sleep/wake — different behaviour, currently sharing the word "resume"; ADR 0005 open item 9 settles whether it is exempt, changed, or renamed. | `grill-with-docs` session, 2026-07-28 |
| Start | Begin tracking when nothing is active. A first-class action as of 2026-07-28, distinct from Switch: `Switch` is deliberately **not** overloaded to mean Start when nothing is active, since one command describing two transitions depending on state weakens the model. `TransitionPayload::Start` already exists in `model.rs`; no command exposes it, and it is currently reachable only implicitly through `switch`. | `docs/concept/concept.md`; made first-class in the Event Model ADR |
| Derived Interruption Status | The **canonical, non-persisted projection** every consumer must use to display interruption state: `NeverInterrupted` \| `Pending` \| `Resumed` \| `Skipped`. Computed from a Time Block plus the current interruption stack — persisted outcome if present; else `Pending` if the block's id appears as a frame's `paused_time_block_id`; else `NeverInterrupted`. Exists because an absent Interruption Outcome is genuinely ambiguous (never interrupted *vs.* interrupted-and-unresolved), and no UI or export may invent its own interpretation. Keeps the persisted model minimal without letting derived views disagree. | Second-pass verification review, 2026-07-28; specified in the Event Model ADR |
| Recovered Gap | An active Time Block reconciled after a detected gap — an ungraceful crash, or a resume from sleep/hibernate — with an end time **inferred** from the last durable write rather than chosen by the user, accurate to roughly the heartbeat interval. Under the three-field model this is `EndDetermination::SystemInferred`; the older `recovered-gap` completion-reason value is retired. Surfaced distinctly and correctable via timeline reconstruction, never silently trusted. | `docs/product/features/interruption-stack.md`; remapped to End Determination 2026-07-28 |
| Capture Rate | Percentage of tracked work minutes whose Capture Origin is live capture, over a rolling working week. **Adjusted blocks still count** — a live capture later corrected is evidence of successful capture with imperfect timing, not of reconstruction. Excluding them would make the metric sensitive to editing habits rather than capture discipline, so that a one-second correction erased the evidence that the task was captured as it happened. Minutes rather than blocks, because one forgotten two-hour meeting matters more than three forgotten five-minute blocks. Provisional target ≥90% — not measured, chosen as a starting hypothesis, revisited after ~4 weeks of real usage. Measures capture **discipline**; pair with Adjustment Rate, which measures capture **accuracy**. | `docs/vision/vision.md`, 2026-07-28 |
| Adjustment Rate | Percentage of live-captured minutes subsequently adjusted (start/end corrected, resized, identity edited). Same unit as Capture Rate so a two-minute correction and a four-hour one don't carry equal weight. Exists because one number cannot express both capture behaviour and capture quality. Diagnostic when read together: high capture / low adjustment is the goal; high capture / high adjustment means capture happens but timing is unreliable; low capture / low adjustment means work is being reconstructed rather than captured. No target set — it interprets Capture Rate rather than passing or failing on its own. | `docs/vision/vision.md`, 2026-07-28 |
| Capture Latency | Time between invoking a capture action and the new work becoming the active tracked task, inclusive of the durable write that `docs/product/features/interruption-stack.md` requires before a transition counts as committed. Provisional target ≤1s, same status as Capture Rate. | `docs/vision/vision.md`, 2026-07-28 |
| Task Template | A reusable preset that pre-populates a Time Block's name/project/client, for fast starts on recurring activities (e.g. daily standup). | `docs/product/mvp.md` |
| Anchor Name | The auto-generated name (`Anchor N`) assigned to a Time Block started without one — e.g. via the Switch/Interrupt hotkeys, which no longer require typing a name first. `N` counts only same-day auto-named tasks and resets each local calendar day. A real name like any other; not a null/placeholder value, and not special-cased by export or aggregation. | `docs/product/features/interruption-stack.md` |
| Rename | Changes the currently active Time Block's name/project/client in place, without affecting its start time, the interruption stack, or any other Time Block. A durably logged transition, distinct from Switch/Interrupt/Return — used to give an Anchor Name task a real name, or to retarget it to an existing Task Template or past task. | `docs/product/features/interruption-stack.md` |
| Torn Write | A write to the persisted transition log interrupted mid-operation (e.g. by a crash), leaving a partial record with no trailing newline. **Detected** via parse-validity plus a checksum framed outside the JSON object ([ADR 0004](decisions/0004-transition-log-format-and-torn-write-scheme.md)), and **removed** at the next `LogWriter::open` by truncating everything after the final record boundary — so the next append always starts on a fresh line. Committed history is never touched: the truncation cannot cross a newline, and only unfinished writes are discarded, which `append` never acknowledged to its caller. **Corrected 2026-07-29:** this entry previously said only that "every prior record is unaffected," which was true but concealed the real failure — until [`78096a8`](https://github.com/DeLicious777/Anchor/commit/78096a8), everything written *after* a torn write was permanently lost, because the next record was appended onto the unterminated fragment. See `docs/risks.md` R5 and issue #18. | `docs/product/features/interruption-stack.md`; detection in ADR 0004, recovery in `app/src-tauri/src/log/writer.rs` |
| Constraint (vs. Preference) | A non-negotiable architectural boundary recorded in `docs/architecture/constraints.md` — distinct from a preference, which can lose to a better trade-off. A preference is promoted to a constraint via an ADR when it's doing the work of eliminating options outright, not just tipping a close call. | `docs/architecture/constraints.md`, first applied in `docs/decisions/0002-desktop-app-framework-and-platform.md` |
